# Inspector rail — design prototype, not app behavior

This isolated Storybook exploration combines the
[MUI mini-variant drawer](https://mui.com/material-ui/react-drawer/#mini-variant-drawer)
with selected [Material 3 navigation rail improvements](https://m3.material.io/components/navigation-rail/overview).
It retains the M2/MUI visual language rather than introducing a separate M3 surface.
It is not imported by the app.
No ImageViewer, routes, production drawers, shared hooks or configuration are changed.
The tissue image and bottom toolbar are static: pan, zoom and image navigation
are deliberately outside this prototype. All data and mutations are mocked.

## Interaction model

One right-anchored MUI `Drawer variant="permanent"` contains both navigation and
content. Its paper stays mounted and animates from `spacing(8) + 1px` (65px with
the current theme) to **300px total**, not 300px plus a separate rail. As in the
MUI demo, width uses `theme.transitions`, sharp easing, and the enteringScreen /
leavingScreen durations. The standard MUI surface, inner-edge divider and
List/ListItemButton/ListItemIcon structure remain; there is no second panel paper.

The top menu/chevron expands or collapses the drawer. A collapsed destination
expands to its content; an expanded active destination collapses it. The menu
button returns to the last-used destination. Icons stay at the outer/right edge
throughout the animation, while labels appear beside them when expanded. Tooltips
name collapsed destinations. The remembered destination retains its pill indicator;
when expanded that indicator spans both icon and label. Theme tokens and `alpha()`
supply interaction states in light and dark, with a keyboard-focus outline.

Selected content renders below the destinations inside that same paper. Long
Inuksuk titles ellipsize; accessible names, title tooltips and ⋮ controls remain.
Switching preserves the content container and shared pin. Active-destination,
chevron and Escape dismissal work even when pinned; menu Escape only closes the menu.

Unpinned expanded drawers overlay the image and retract on an outside pointer press,
including mouse and touch. Inside-menu and Board-picker interactions do not count
as outside presses. The mini strip always reserves its own width. Pinning grows
that reservation to the full 300px, so expansion takes only another 235px from the
image. Unpinning restores the mini reservation without closing the drawer.
At xs (below 600px), the strip is `spacing(7) + 1px` (57px), with icon-only 48px
destination targets. Content remains a bottom sheet, occupying the lower 60% next
to the strip; pinning reserves height instead of width. Both are regions of the
same drawer paper, with pointer-transparent space above the sheet so image presses
still reach the canvas and collapse an unpinned inspector.

### M3 differences adopted, and deliberately not adopted

The overview's **Differences from M2** lists predictive back, new color mappings /
dynamic color compatibility, and a contrasting pill-shaped active indicator.
This hybrid adopts the **pill indicator**, using MUI theme palette tokens and
`alpha()` rather than replacing the app palette with M3 color roles. It does **not**
implement OS predictive back or dynamic/wallpaper-derived color. The MUI surface,
typography, divider, spacing and controls remain; this is not an M3 theme migration.
The current M3 rail also supports a menu-controlled collapsed/expanded form with
labels beside icons when expanded; those behaviors are adopted instead of a
separate rail-plus-drawer. No FAB, additional destinations, modal backdrop or
mobile navigation-bar conversion is introduced for this two-tool inspection task.

The shared pin uses `usePinnedDrawerState('storybook',
'prototype-inspector-rail', false)`: storage synchronization is disabled, so it
neither reads nor changes a user's real drawer preference. Visibility toggles
also use prototype-local memory, not app localStorage.

## Real components, prototype-only layout

- Details embeds the real `ImageDetailsDrawer` metadata and viewer instructions.
- Inuksuks embeds the real `ImageInuksuksDrawer` list, group controls and menus.
- Placement uses `InuksukFormDialog` with mock services; Title, Board and collapsed
  More options remain real controls. The form moves inline above the list when
  Inuksuks is open; otherwise it floats top-right. Draft values survive the move.
- Marker information uses the real `InuksukInfoCard`, positioned beside the marker
  instead of in the inspector. Its Board-name request is mocked in story setup.
- Favourites use stars: the info card already renders `Star`/`StarBorder`; a
  prototype-local MUI theme gives the form's Favourite checkbox the same star
  icons, including inside More options. No production theme or component changes.

### Production favourite audit (read-only)

`BoardsPage.tsx` uses `Favorite`/`FavoriteBorder` hearts for Inuksuk card actions
and the read-only favourite badge. `InuksukFormDialog.tsx` uses a standard checkbox,
not a heart. `InuksukInfoCard.tsx` already uses `Star`/`StarBorder`. The source-wide
heart/Favorite search found no other Inuksuk favourite icon sites. Production
inconsistencies are reported for follow-up, not changed by this prototype.

Prototype-only wrappers neutralize the drawers' original positioning and hide
their individual headers; the shared drawer supplies the title, pin and top chevron.
The real components are deliberately untouched. These CSS adapters are not a
proposed production extraction. Save/Edit/Delete show a prototype-only message;
they never write to the backend. The popover uses a fixed illustrative anchor,
not production collision detection or an OpenSeadragon projection.

## Open product questions

1. **Left/right role split:** should the left side remain navigation (Boards,
   collections, sequence filmstrip) while the right is exclusively inspection and
   editing? Would moving Inuksuks to the right disrupt established navigation?
   This prototype does not remove or redesign any left-side app controls.
2. **Where should marker information live?** A marker-adjacent popover provides
   spatial context, but can obscure the detail and needs edge/collision handling.
   The inspector is predictable and scrollable but separates the card from its
   point. Should mobile always use the bottom sheet instead of a popover?
3. Should a pinned inspector be closable by its active icon, and should its tool
   selection/pin survive navigation? This prototype chooses closable, in-memory
   state only; it does not prescribe an app persistence contract.
4. How should an unsaved placement coexist with Details? Here it floats when the
   Inuksuks content is not visible, retaining the draft; evaluate whether forcing
   the Inuksuks tab or keeping the form always docked would be clearer.
