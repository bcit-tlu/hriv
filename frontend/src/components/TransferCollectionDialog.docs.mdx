## When to use

`CollectionsPage` opens this dialog from the **Transfer** action on a card or the detail
header — both gated on `collection.permissions.canTransfer`. It is also the admin flow for
reassigning an **orphaned** collection found via the owner filter's _No owner (orphaned)_
option.

## Interactive example

Use the `role` control to compare the admin and instructor pickers.

## Implementation guidance

- **Target kinds.** `POST /api/collections/{id}/transfer` takes exactly one of
  `user_id` / `program_id` plus `version`. Admins get an _A user_ / _A program_ choice;
  instructors go straight to a program select narrowed to their own `program_ids`.
- **Users come from the auth context.** The admin user picker reads `auth.users` (loaded at
  login, refreshed on open) and hides inactive accounts — the backend 422s them anyway.
- **Same-owner guard.** The confirm stays disabled until a target different from the current
  owner is chosen.
- **Errors stay in the dialog.** 403 (target outside your authority), 409 (stale `version`),
  and 422 (invalid/inactive target) surface via `userMessage`; a successful transfer closes.
- **Orphaned collections** show an info hint — assigning an owner restores normal management.
