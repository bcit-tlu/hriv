## When to use

`App` renders `CollectionsPage` when the active page is `collections`
(`?page=collections`, `?page=collections&type=sequence|synchronized`, or `?collection={id}`).
The unified page offers three views — Cards, Table, and a Graph powered by the collections
graph endpoint — switched by the toolbar toggle; the view choice is intentionally not persisted
(the page always loads on Cards while Table/Graph are evaluated). `?type=` seeds the
shared Type filter instead of picking a sub-page (#1629). It is
visible to every authenticated role, including students. The component is presentational —
list/detail data and mutations come from `useCollectionsData` via props, so the stories drive it
with deterministic fixtures.

## Implementation guidance

- **Filters.** A shared `FilterBar` (the Manage-page pattern) sits above all three views with
  popover facets: **Name** (debounced 300 ms into `filters.q` — a server-side substring filter
  over name/description/owner in Cards/Table, dims non-matching graph nodes), **Type**
  (single-select; `?type=` deep links seed it and clearing
  drops the URL parameter), **Owner** (**My collections** for every role — selecting it clears
  the owner facet — plus named owners for admin/instructor/staff from `GET
/api/collections/owners` and _No owner (orphaned)_ for
  admins; the hook never sends `orphaned` for other roles and never sends
  `owner_user_id` / `owner_program_id` for students), **Visibility** (server-side
  `visibility=` multi-select; dims non-matching graph nodes) and **Category**
  (server-side `category_id=`, ancestor-aware — a parent matches collections filed anywhere
  beneath it; dims non-matching graph nodes). While any facet is active
  the bar shows deletable summary chips and a **Clear all** action.
  `normalizeCollectionFilters` applies both owner rules to the hook's filter state, so an owner
  selection left over from a previous user is dropped rather than hiding the new user's own
  saves.
- **Server paging and sorting (#1631).** Cards and Table share one server-side page state owned
  by `useCollectionsData` (`page`, `pageSize`, `sort`, `total` props): requests carry
  `page`/`page_size`/`sort`/`direction` and the `X-Total-Count` header drives the shared
  `TablePagination` footer shown under both views. Filter, sort or page-size changes reset to
  page 1, the background poll refetches the current page, and bulk selection survives page
  changes (off-page rows stay selected). The Graph view flips the hook to its `full` list mode —
  an unpaged request, facets used for highlight only.
- **Table columns.** In Table view the FilterBar's **Choose columns** action opens
  `ColumnVisibilityDialog` (per-user persisted visibility and order): Cover, ID, Name, Type,
  Scope, Description, Category, Images, Owner, Programs, Groups, Visibility, Created, Updated —
  default visible set is Cover, Name, Type, Category, Images, Owner, Updated, plus Visibility
  for admins/instructors. Students are never offered Visibility. Every column except Cover,
  Programs and Groups sorts (server-side); ID/Images/Created/Updated open descending.
- **Table rows (merged Manage → Collections, #1554/#1567/#1578).** The Table view is the only
  collections table. Hidden and category-hidden rows dim (own-hidden adds the eye-off marker;
  a hidden filing category locks the Visibility switch). Category cells are breadcrumb links
  to Browse; Programs/Groups show the collection's own scope chips plus the filed category's
  inherited chips. Row click opens the collection; the row menu offers View, Edit (owners and
  curators) and Manage owners (`canTransfer`). A selection column (curators: any row; others:
  rows they could delete) drives **Bulk Edit (N selected)** → `BulkEditCollectionsDialog`.
  Old `?page=manage-collections` links open this page on Table.
- **Grid.** One column on phones, two at `sm`, three at `md`, four at `lg`, each cell a
  `CollectionCard`.
- **States.** Spinner while the first page loads, a plain error `Alert` (no action), and an
  empty state whose copy changes depending on whether filters are active; with no filters the
  copy's **Create a collection** is a link that opens the same dialog as **New collection**.
- **Create / edit.** Both use `CollectionEditDialog`. Editing from a card first loads the full
  record (summaries omit the restricted scope); editing from the detail header reuses the loaded
  detail.
- **Student collection count caps.** The **New collection** button stays enabled until
  both types are capped. Since the visible list is type-filtered, the page fetches all of the
  student's collection summaries to determine both caps; the create dialog disables capped types
  and selects the other type when its default type is capped.
- **Delete.** Lives inside `CollectionEditDialog` only (#1554, the `EditImageModal` pattern):
  first click arms, second click confirms; a failure keeps the dialog open with the API message.
  Deleting the currently open collection returns to the list.
- **Detail.** The header leads with a `CategoryBreadcrumb` of the collection's filed location
  (category ancestors, or just **Home** at the root) instead of a back link (#1559); each link
  navigates Browse to that spot via `onNavigateCategory`. The top-right row orders: visibility
  chip, **Manage** (`canEdit` — opens
  `CollectionManageDialog` for reorder/add/remove, #1566), **Edit**, and
  **Hide collection** / **Show collection** (`canHide`, wired to
  `onToggleHidden`) — or, when the filed category is hidden, a disabled
  **Hidden by Category** state (the image view / edit dialog convention).
  Owners management is a pencil beside the owner name
  (`canTransfer`), and hidden collections show through greyscale alone — no
  `Hidden` chip (#1567); a hidden filing category desaturates the same
  controls and the sequence filmstrip. Filing a collection into a category moved into the edit dialog's category
  picker — the header no longer carries a separate **Move** button (#1566). `sequence` collections mount
  `SequenceCollectionViewer` and `synchronized` collections mount
  `SynchronizedCollectionViewer` (see their own docs pages). A 404 (`detailError`) renders the
  not-found alert with a way back to the list.
