# Backend (FastAPI + SQLAlchemy + Alembic)

All commands run from `backend/`.

## Commands

- Install dependencies: `poetry install --with dev`
- Dev server: `poetry run uvicorn app.main:app --reload`
- Tests: `poetry run pytest` — enforces an 80% coverage gate via `addopts`
  in `pyproject.toml`; `pytest-asyncio` runs in auto mode (no
  `@pytest.mark.asyncio` decorator needed)
- Apply DB migrations: `DATABASE_URL=... poetry run python -m app.migrations_bootstrap`
- New migration: `DATABASE_URL=... poetry run alembic revision --autogenerate -m "<message>"`

## Conventions

- PEP 8 and existing code conventions; type annotations on function
  signatures.
- Write unit tests for new functions; aim for >80% coverage; run
  `poetry run pytest` before committing.

## Schema changes (Alembic)

Alembic is the sole source of truth for the schema. Change
`app/models.py`, generate a revision with the command above, review the
autogenerated output by hand (autogenerate is a heuristic), and commit the
migration alongside the model change. See `README.md` (Database migrations)
and [`docs/domain-model.md`](../docs/domain-model.md).

**Alembic revision IDs must be ≤ 32 characters.** `alembic_version.version_num`
is `VARCHAR(32)`, so an over-length `revision` id only fails at fresh-DB
bootstrap (`migrations_bootstrap` / docker-compose `migrate` service) — it is
invisible in CI and on already-migrated DBs. Keep ids short (e.g.
`0016_admin_task_orig_filename`, not `0016_add_admin_task_original_filename`)
and verify a fresh bootstrap before merging. Renaming an over-length head
revision (id + filename) is safe — no DB can ever have persisted it.
